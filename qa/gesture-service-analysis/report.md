# Исследование XCGestureService

Дата: 2026-10-07. Только статический анализ APK и сохранённой выгрузки OneOS. На ГУ ничего не устанавливалось и не менялось; сейчас через ADB доступен только эмулятор. Реальная установка, перезагрузка и доставка касаний на ГУ не проверены.

## Главный вывод

На G636 из сохранённой выгрузки проблема объясняется не потерей системных разрешений из-за `/data`, а возвратом более новой системной версии при загрузке. У APK из Downloads `versionCode=19`; у штатного пакета с тем же именем — `786`. В штатном коде обработчики двух, трёх и пяти пальцев не подключены. Поэтому после установки старой полной реализации жесты появляются, а при возвращении штатной пропадают. Это сильная гипотеза для описанного пользователем поведения, подтверждённая кодом обоих APK и PackageManager, но ещё не проверенная сравнением состояния конкретного ГУ до/после ребута.

Уточнение пользователя: установка обычная; после ребута, по его наблюдению, остаётся стандартный пакет и мультитач не работает. Это согласуется с откатом, но не заменяет измерения версии/пути. Как конкретный OEM-установщик разрешает установку версии 19 поверх более высокой версии, здесь не исследовано.

Дополнительно: у старого APK нет BootReceiver. Если на другом ГУ он остаётся активной версией после ребута, отдельно требуется запуск его процесса. На нашем OneOS существует штатный путь запуска через LifeControlService; Atlas уже отправляет необходимый сигнал HOME.

## Как получает касания

Цепочка:

`GApplication.onCreate()` → `GestureService.onCreate()` → `GestureContext` → `EdgeEventAPI` → Binder `EcarxInputDispatcherService` в `system_server` → `IInputFilter` → обработчики жестов.

- `GestureContext.startPublisher()` регистрирует прямоугольную область с приоритетом `NORMAL`.
- `EdgeEventAPI` получает `ServiceManager.getService("EcarxInputDispatcherService")` и вызывает `registerPointerEventListener`.
- Это глобальный OEM-фильтр ввода. Он получает `MotionEvent` над чужими приложениями и может пропускать/поглощать события.
- Accessibility-служба `AppWatcherService` отслеживает смену окна/приложения. Распознавание мультитач-жестов выполняется не через Accessibility.
- `AppWatcherService.start()` сам добавляет службу в `enabled_accessibility_services` через системные разрешения. При адаптации нельзя затирать список остальных служб.
- Область старого APK: левый отступ 50 dp, верхний 0, нижний 80 dp. В ветке G636 ширина принудительно задаётся 2830 px. OEM окна местами имеют высоту 1680 px и используют дисплей 2. Это не универсальная геометрия для произвольного устройства.

В декомпилированном `reference-apks/framework/services.jar`, метод `EcarxInputDispatcherService.registerPointerEventListener`, нет явного Java-контроля UID или permission: устанавливается фильтр, сохраняется PID и callback. Это делает собственное подключение интересным направлением, но не доказывает доступность обычному APK: остаются получение Binder через ServiceManager, SELinux, скрытые API и обратная доставка событий. В этой прошивке есть и интерфейс наблюдения `registerTouchEventListener`, но анализ этого класса не подтвердил действующий путь отправки всех касаний в него; рассчитывать на него без отдельной проверки нельзя.

## Реализованные действия

| Жест | Действие | Реальная зависимость |
| --- | --- | --- |
| Два пальца вверх/вниз, оба в левой четверти экрана | Температура водителя | `ICarFunction`, `HVAC_FUNC_TEMP`, зона 1 |
| Два пальца вверх/вниз, оба в центральной половине | Громкость | В G636 — automotive volume groups через `CarAudioManager`; в другой ветке — `AudioManager` |
| Два пальца вверх/вниз, оба в правой четверти | Температура пассажира | `ICarFunction`, `HVAC_FUNC_TEMP`, зона 4 |
| Три пальца вверх/вниз | Яркость дисплея | `ICarFunction`, для центрального дисплея свойство 688063744; отдельное свойство для пассажирского |
| Три пальца горизонтально | Перенос приложения на пассажирский дисплей/обратно; для поддерживаемой навигации — взаимодействие с приборкой | OEM MultiWindow, NaviManager, DIM; зависит от комплектации и активного приложения |
| Сведение пяти пальцев | Недавние приложения | Явный запуск `com.geely.recents/.RecentsCsdActivity`; код также считает четыре пальца как пять |
| Касания/длительное отсутствие касаний | Гашение/пробуждение, экранная заставка | `ScreenFingerObserver`, screensaver, питание/пассажирский дисплей/датчики/VR |

Сведение пальцев открывает именно OEM Recents, хотя внутренние имена содержат `home`/`SCALE_TO_HOME`. Ключи `Gestures_home`, `Gestures_back`, `Gestures_multiwindow` объявлены, но их отдельных обработчиков в исходном APK нет. Боковой однопальцевый Back в нашей выгрузке реализован отдельно внутри `EcarxInputDispatcherService` в framework.

Громкость и яркость блокируются для ряда OEM приложений: Amap, Baidu, Geely map/gallery/settings, HiCar и `com.kanzi.skim`. Температура дополнительно не меняется поверх штатного HVAC. Для мультитач нужны оба пальца в одной зоне. При переносе есть проверки типа экрана, приложения и blacklist. Гарантировать весь набор для Atlas без проверки нельзя.

## Что отключено в наших APK

В старом APK `GestureContext.initObservers()` создаёт:

1. `FiveFingerObserver`.
2. `ThreeFingerObserver`.
3. `DoubleFingerObserver`.
4. `ScreenFingerObserver`.

В G636 `1.0.20250623G(312)` и City `1.0.20260326G(87)` создаётся **только `ScreenFingerObserver`**. Для G636 проверено также по smali, а не только результату JADX. В методе нет ветвления по настройке, возвращающей три остальных обработчика. Установка `Gestures_DoubleFinger_Slide=1`, `Gestures_ThreeFinger_Slide=1`, `Gestures_FiveFinger_Grab=1` не восстановит отсутствующую регистрацию.

Почему производитель убрал подключение — из кода не установлено. Нельзя утверждать, что это просто региональный флаг. Более новая дата версии City тоже не делает её подходящей заменой: `135 < 786`, и обработчики также не подключены.

## Почему исчезает после перезагрузки

В сохранённом `dumpsys-package.txt` G636:

- `userId=1000`;
- `codePath=/system/app/oneOS_ScreenGestureService`;
- `versionCode=786`;
- компонент `.BootReceiver` зарегистрирован на `BOOT_COMPLETED`.

У APK из Downloads версия 19, нет receiver вообще и нет `RECEIVE_BOOT_COMPLETED`. Его `MainActivity.onCreate()` сразу делает `finish()`, но создание процесса запускает службу через `GApplication`. `GestureService.onStartCommand()` возвращает `START_STICKY`: это может восстановить убитую службу в текущей загрузке, а не автоматически запустить APK после ребута.

В `PackageManagerService` нашего `services.jar` вычисляется:

`isSystemPkgBetter = scanSystemPartition && isSystemPkgUpdated && newPkgChangedPaths && newPkgVersionGreater`.

Если системный APK новее установленного `/data`-обновления, удаляются ресурсы обновления и включается системный пакет. То же правило подтверждено [исходниками AOSP Android 11](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/refs/tags/android-11.0.0_r1/services/core/java/com/android/server/pm/PackageManagerService.java), блок `isSystemPkgBetter`.

Таким образом, разрешённый downgrade при установке не отменяет выбор более новой версии при следующем сканировании системы. На G636 это последовательность: полная версия 19 работает → ребут → версия 786 снова активна → мультитач-обработчиков нет. Проверка на живом ГУ остаётся необходимой.

В нашем Launcher уже есть `com.android.launcher3.startup` в первом `onResume`, запускающий последнюю стадию LifeControlService, в том числе GestureService. Связь и прежняя проверка описаны в `qa/launcher-startup-stage/report.md`. Добавлять ещё один автозапуск без диагностики отката бессмысленно.

## Варианты без переустановки APK при каждой загрузке

| Вариант | Оценка |
| --- | --- |
| Оригинальный OEM-подписанный APK с нужными обработчиками и versionCode не ниже системного | Самый простой способ сохранить оригинальные глобальные жесты. Желательно строго выше системного для обычного обновления. В исследованных файлах подходящего нет. Важен числовой versionCode, а не дата/номер в versionName. Нужен также путь запуска после загрузки. |
| Собственные жесты в окне AtlasLauncher | Реализуемо обычными Android API без OEM-подписи для получения касаний в своём окне. Переживает ребут вместе с настройками приложения. Не работает поверх навигации/плеера/других приложений; OEM-действия климата/яркости проверяются отдельно. |
| Отдельный компонент с собственной реализацией глобальных жестов через OEM input dispatcher | Предпочтительное направление для нашего управления жестами без замены штатного пакета. Сначала диагностический прототип регистрации callback от нашего UID. Если доступ закрыт — небольшой помощник, запускаемый с доступными повышенными правами через проверенный root/Telnet-путь; приложение сохраняется в `/data`, повторная установка не нужна. Наличие root shell не доказывает, что процесс сможет работать с нужным Binder/SELinux-контекстом. |
| Замена APK в `/system` или загрузочный overlay системного файла | Сохраняет OEM-подпись исходного APK, но требует решения Verified Boot/прав записи либо существующего механизма overlay; добавляет риск загрузки и OTA. В выгрузке включён verified boot, поэтому обычное копирование через ADB не является готовым решением. Для первой реализации не рекомендуется. |
| Изменить versionCode старого APK, переподписать, переименовать пакет | Не решает задачу сохранения оригинальных системных прав: изменение ломает OEM-подпись; OEM private key отсутствует. Даже размещение переподписанного APK в `/system` не заменяет platform signature для shared UID. |
| Только запускать исходную службу после загрузки | Подходит лишь если после ребута исходный APK остаётся активной версией. Возврат к урезанному системному APK не исправляет. |

Для глобального компонента самый простой первый набор — центральный двухпальцевый жест громкости, трёхпальцевый яркости и сведение пальцев для Recents. Климат требует отдельной проверки зон, границ температуры и синхронизации. Перенос между дисплеями/проекция навигации не являются универсальными жестами для однодисплейного ГУ.

Полноэкранный overlay обычного APK не является прозрачной заменой OEM-фильтру: окно, получающее касания, может лишить их нижележащее приложение. Accessibility на Android 11 распознаёт мультитач при touch exploration, который меняет обычное взаимодействие; это не пассивный OEM-фильтр. См. [AccessibilityServiceInfo](https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#FLAG_REQUEST_MULTI_FINGER_GESTURES).

Собственная реализация через OEM фильтр тоже должна сохранять обработку обычных касаний и учитывать конкуренцию с фильтром штатной заставки. Это обязательный предмет проверки на ГУ, а не повод автоматически заменить/отключить штатный сервис.

## Минимальная диагностика на ГУ

До и после перезагрузки выполнить одни и те же команды, адресовав их реальному serial:

```sh
adb -s SERIAL shell pm path com.geely.screengestureservice
adb -s SERIAL shell dumpsys package com.geely.screengestureservice
adb -s SERIAL shell dumpsys activity services com.geely.screengestureservice
adb -s SERIAL shell dumpsys EcarxInputDispatcherService
```

Сравнить codePath, versionCode/versionName, UID, enabled/stopped и присутствие фильтра. Если до ребута `/data` и 19, после `/system` и 786 — откат доказан. Если после ребута сохраняется `/data` и 19, но службы нет, проверяется запуск уже установленного экспортированного компонента, без повторной установки:

```sh
adb -s SERIAL shell am startservice -n com.geely.screengestureservice/.GestureService
```

Команда запуска здесь приведена как последующий диагностический шаг, на устройство не отправлялась. При versionCode 786 запуск не вернёт мультитач: в этой версии обработчики отсутствуют. Не очищать данные, не отключать штатные системные компоненты, не менять HOME ради этой проверки.
