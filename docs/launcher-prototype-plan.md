# Первый прототип AtlasLauncher для OneOS

Статус 2026-09-26: **портретное HOME-приложение 0.4.0 с каталогом приложений и сеткой виджетов собрано; основные сценарии проверены на эмуляторе; проверка OneOS на ГУ не выполнена**. Основание по OEM-поведению — статический анализ APK из [`reference-apks`](../reference-apks/README.md) и кода GInputBridge. Подключён только эмулятор, ГУ через ADB недоступно.

## Цель и границы прототипа

Сделать отдельное устанавливаемое HOME-приложение с настраиваемым списком установленных приложений и размещением обычных Android AppWidget на главном экране. Сохранить работу нижней панели климата/dock и верхней выдвижной панели OneOS на HOME-экране и после запуска приложений. Штатный лаунчер остаётся установленным и доступным для возврата.

Первый прототип не переписывает климат, не подменяет SystemUI и не пытается встроить Activity других приложений внутрь рабочего стола. Достаточно одного рабочего экрана с виджетами, списка приложений и настроек размещения. Дополнительные страницы, изменение размера ярлыков и собственная глобальная панель быстрых настроек идут после проверки системных панелей.

## Что установлено по файлам

| Область | Факт | Следствие |
| --- | --- | --- |
| Штатный HOME | `oneOS_Launcher3.apk` объявляет `MAIN`/`HOME`, работает с `android.uid.system`; в `assets/system_app_config*.json` и `res/xml/widget_whitelist.xml` есть OEM-списки приложений/виджетов | Новый APK может объявить HOME и вести свой каталог без OEM-списков, но не получает системный UID и привилегии штатного лаунчера |
| Нижняя панель | `oneOS_SystemUIPlugin.apk` имеет `android.uid.systemui`, классы `DynamicDockBar`, `DockStateMachine`, климатические ресурсы и интерфейс `IDockBarService` | Нижняя панель — отдельный системный слой, а не часть разметки Launcher3; нельзя считать, что смена HOME её автоматически сохранит или уберёт |
| Верхняя панель | `SystemUI.apk` содержит системные Quick Settings; OEM-плагин содержит `StatusBar`, ресурсы `status_bar_g636/g733` и всплывающие окна | В первую очередь следует оставить OEM-жест и OEM-панель; замена всего системного слоя требует другого уровня прав |
| Управление dock | В исходниках GInputBridge есть `DockBarManager` с `DOCK_SHOW_ALL=1`, `DOCK_SHOW_LINE=2`, `DOCK_HIDE=3` и `showDock()`; `OneOSApiManager` запрашивает сервис типа 21 | Есть точка для адресного эксперимента, если OneOS скрывает dock для нового HOME. Доступность и устойчивость вызова на ГУ не проверены |
| GInputBridge | APK 4.6.1 и исходники объявляют `LauncherEntryActivity`/`AppLauncher` как `LAUNCHER`, а собственный экран рисуют через `TYPE_APPLICATION_OVERLAY`. Есть экспортируемый `BackgroundTaskReceiver` с `CAR_FUNCTION`, `GET/SET_*_PROPERTY` и другими действиями | Использовать GInputBridge как установленный помощник можно, но его overlay не является HOME; для собственного лаунчера нужен отдельный HOME-компонент. Существующие широкие broadcast-команды не считать безопасным универсальным IPC для нового UI |
| Виджеты | `oneOS_MediaCenterUI.apk` объявляет несколько `android.appwidget.provider`; часть провайдеров и интерактивных функций завязана на разрешения/интеграцию Launcher3 | Обычные AppWidget размещать через платформенный host с пользовательским подтверждением привязки. OEM-медиавиджет проверять отдельно и не делать условием готовности первого прототипа |
| Сторонний обход климата | SCS содержит настройку `hideClimatePanelOnAppOpen` и ссылку на запуск `com.ecarx.xcapa` | Этот способ скрывает панель и противоречит цели прототипа; не переносить его в AtlasLauncher |

В наборе пока нет `com.geely.hvac` и `com.geely.service.oneosapi`. Для первого прототипа их не нужно встраивать; если потребуется изменять OEM-панель, сначала получить эти APK или подтвердить вызовы на живом ГУ.

## Решение для первого прототипа

### 1. Отдельное HOME-приложение

Создать в этом репозитории небольшой Android-проект с отдельным package name (рабочее имя `com.mmwtl.atlaslauncher`). Основной `HomeActivity` объявить как `ACTION_MAIN` + `CATEGORY_HOME` + `CATEGORY_DEFAULT`. Не использовать `TYPE_APPLICATION_OVERLAY` как основной рабочий стол: overlay GInputBridge рассчитан на вызов поверх другого приложения и не решает жизненный цикл HOME, переключение задач и размещение AppWidget.

Приложение не просит системные разрешения Launcher3 и не заменяет его APK. На этапе установки выбор HOME выполняется штатным диалогом/настройкой OneOS. До проверки этого сценария нельзя обещать, что OEM позволит сделать сторонний HOME постоянным.

### 2. Сохранение системных панелей как исходный режим

На `HomeActivity` использовать обычное окно без immersive/fullscreen, без принудительного скрытия status/navigation bars и без оконных флагов, отнимающих жест сверху. Разметить контент по фактическим `WindowInsets` и результату проверки на ГУ. Не рисовать кнопки или виджеты под областью dock и верхнего статус-бара. Не отправлять команды `DOCK_HIDE`, `canSlide(false)` и не запускать xCapa ради смены видимости.

**Главный технический риск:** OEM SystemUI может различать штатный `com.android.launcher3` и сторонний HOME по пакету, UID либо состоянию окна. Тогда нижний dock или верхний жест могут вести себя иначе, хотя сам Android считает AtlasLauncher домашним экраном. Это проверяется на устройстве раньше оформления UI.

### 3. Список приложений

Получать запускаемые Activity через `LauncherApps`/`PackageManager` для `ACTION_MAIN` + `CATEGORY_LAUNCHER`, хранить идентичность как `ComponentName`, а не только package name: один пакет может иметь несколько ярлыков. Показывать все доступные пользователю обычные приложения, включая установленные вручную. Для OEM-компонентов без экспортируемой запускаемой Activity не обещать запуск по одному имени пакета.

Минимальный интерфейс: сетка «Избранное» на HOME, кнопка «Все приложения», поиск по локальному названию, добавление/удаление из избранного и порядок избранного. Обновлять каталог по изменениям пакетов и при возвращении на HOME. Запускать выбранную Activity стандартным launcher intent. Ярлык возврата к штатному HOME/настройкам OneOS оставить доступным в интерфейсе прототипа.

### 4. Виджеты

Добавить один контейнер для стандартных Android AppWidget на HOME. Использовать `AppWidgetHost`/`AppWidgetManager`: выбор провайдера, выделение ID, системный запрос привязки, конфигурационную Activity провайдера при наличии, `startListening`/`stopListening`, удаление ID и восстановление сохранённого размещения после перезапуска процесса. Размеры и координаты хранить отдельно от ID виджета. Для MVP достаточно фиксированной сетки слотов, чтобы виджеты не перекрывали dock и друг друга.

Первой проверкой взять простой сторонний AppWidget без OEM-зависимостей. Затем попробовать виджет из `com.geely.mediawidget`; если он требует Launcher3-специфичный доступ или ломается в новом host, зафиксировать ограничение отдельно. Не строить весь HOME вокруг успешности именно OEM-медиавиджета.

### 5. Связь с GInputBridge

Для показа приложений и обычных виджетов GInputBridge не требуется. Для первого прототипа не копировать в новый APK `adaptapi`, `com_geely` и автомобильные API. Если понадобятся кнопки автомобильных функций, использовать уже установленный GInputBridge как исполнитель, но согласовать маленький явный контракт: ограниченный список именованных команд, ответ о результате/текущем состоянии, проверка вызывающего приложения и версии контракта.

Существующий экспортируемый `BackgroundTaskReceiver` принимает, в частности, `CAR_FUNCTION`, операции с произвольными property ID и `ADB_COMMAND`. Прототипу не следует считать его произвольные SET/ADB-команды интерфейсом настроек. Для первой интеграции достаточно одной безопасной команды, если она действительно нужна UI. Для управления dock через GInputBridge потребуется отдельный адресный вызов `DockBarManager` и проверка сервиса на ГУ; в текущем коде приложения вызова `getDockBarManager()` нет.

### 6. Верхняя панель: решение по результату проверки

Предпочтение — штатная верхняя панель OneOS без изменений. Если она открывается поверх нового HOME и нормально закрывается, собственную копию не делать.

Если именно на HOME OEM-жест недоступен, сделать на экране лаунчера **локальную** раскрывающуюся панель быстрых действий с настраиваемыми элементами: запуск настроек/приложений и только подтверждённые команды GInputBridge. Она будет работать на HOME-экране; сделать её заменой системной панели поверх всех приложений обычным HOME-APK нельзя. Такая ветка требует отдельной проверки поведения и доступности штатных критичных функций.

## Последовательность реализации и проверки

Статусы отражают текущую реализацию. Аппаратные проверки остаются открытыми до подключения ГУ.

1. **[ ] Проверить базовое поведение OneOS на ГУ.** Подключить ADB, записать текущий HOME, версию прошивки/разрешение, сделать скриншоты и точечные `dumpsys window`/`dumpsys activity` для штатного HOME, открытого верхнего меню и dock. Зафиксировать способ безопасно вернуться к штатному HOME. Ничего не отключать и не удалять.
2. **[x] Собрать HOME-прототип.** HOME Activity без overlay и автомобильных API собран в APK и открыт через системный выбор HOME на эмуляторе. Проверка холодного старта, Home/Back и пробуждения именно ГУ перенесена в аппаратную приёмку (шаг 8).
3. **[ ] Принять решение по панелям.** На новом HOME проверить видимость и нажатия нижнего dock/климата, верхний жест, открытие/закрытие верхней панели, возврат после запуска нескольких приложений. Сопоставить скриншоты и окна `dumpsys` со штатным HOME. Если dock пропадает, отдельно проверить адресный `DockBarManager.showDock(DOCK_SHOW_ALL)` через установленный GInputBridge и устойчивость результата при смене Activity. Не делать постоянный таймер вызовов как обход OEM-политики.
4. **[x] Реализовать приложения.** Каталог Activity, избранное с порядком, поиск и запуск реализованы; каталог обновляется при возврате на HOME. Поиск, закрепление Clock и запуск из списка/избранного проверены на эмуляторе. OEM-приложение и пакет с несколькими ярлыками требуют ГУ.
5. **[x] Реализовать виджеты.** Выбор, привязка, настройка, отображение, сохранение, перемещение и удаление реализованы. Привязка Analog clock и его сохранение после force-stop проверены на эмуляторе. Geely MediaWidget, управление порядком/удалением через UI и перезапуск ГУ пока не проверены.
6. **[ ] Добавить только необходимую интеграцию с GInputBridge.** Если по шагам 3–5 есть конкретная недостающая функция, реализовать узкий вызов и отображать ошибку/недоступность исполнителя. Не зависеть от GInputBridge для открытия HOME и списка приложений.
7. **[ ] Проверить альтернативу верхней панели только при подтверждённой необходимости.** Локальная панель на HOME с настраиваемым набором действий. Снова проверить, что OEM-жесты и климат не перехватываются.
8. **[ ] Финальная проверка прототипа на ГУ.** Перезагрузка, запуск без сети и с GInputBridge выключенным, переходы между приложениями, сохранение виджетов, возврат к штатному лаунчеру. Приложить APK, скриншоты и короткий протокол известных ограничений. Эмулятор/сборка не заменяют эту проверку.
9. **[x] Обновить оформление HOME под портретный ГУ.** Крупные кнопки, карточки виджетов/избранного и новый каталог приложений реализованы; оставлена только портретная компоновка и Activity закреплена в портретной ориентации. Финальный APK установлен поверх предыдущего на эмуляторе, виджет и избранное сохранились, портретный экран и системная привязка второго виджета проверены. Расположение относительно OEM dock потребует шага 8.
10. **[x] Перекомпоновать HOME по визуальному ориентиру Femto Car Launcher.** Добавлены свободный декоративный фон, плавающие часы, карточка AppWidget и горизонтальный док избранного. Каталог, выбор виджетов и сохранение после перезапуска процесса проверены на портретном эмуляторе. Живую карту не добавляли: ей потребуются отдельные навигационные данные и проверка на ГУ.
11. **[x] Разместить виджеты как на обычном рабочем столе.** Убраны общая лента, внешние карточки и жёсткие размеры. Координаты и размеры сохраняются по AppWidget ID, прежние привязки мигрируют; режим редактирования позволяет перетаскивать, изменять размер при поддержке провайдера и удалять. На эмуляторе проверены обновление поверх 0.3.0, появление старых виджетов без действий, перемещение и изменение размера Search, запуск Search по нажатию, сохранение после перезапуска и добавление Digital clock. Совместимость конкретных OEM-виджетов требует ГУ.
12. **[x] Привязать виджеты к сетке.** Новые виджеты и старые свободные координаты занимают свободные ячейки; перенос ищет ближайшее доступное место, изменение размера округляется до ячеек и отклоняется при пересечении. На эмуляторе проверены перенос в занятую область, отклонение пересекающего изменения размера и сохранение прежних AppWidget ID.

## Критерии готовности первого прототипа

- AtlasLauncher выбирается HOME без удаления штатного Launcher3; возврат к штатному HOME выполняется без очистки данных.
- На HOME можно открыть приложение из полного списка и закрепить его в избранном; установленное вручную приложение появляется после обновления каталога.
- Хотя бы один обычный AppWidget переживает перезапуск процесса и ГУ без повторной привязки.
- Нижняя климатическая панель видна и реагирует на нажатия, верхняя панель открывается и закрывается как на штатном HOME. Если OEM блокирует один из этих пунктов, результат явно отмечен как нерешённый и не заменён предположением.
- Отсутствие GInputBridge не ломает HOME, приложения и обычные виджеты; зависимые кнопки показывают недоступность.

## Риски и решения

| Риск | Как проверить | Решение в прототипе |
| --- | --- | --- |
| OneOS закрепляет штатный HOME или переустанавливает его после запуска/перезагрузки | Выбор HOME, перезагрузка, `cmd package resolve-activity`/`dumpsys activity` | Не удалять штатный пакет; рассматривать overlay GInputBridge только как отдельный режим, не выдавая его за полноценный HOME |
| OEM dock меняет размер/скрывается для стороннего пакета | Снимки + `dumpsys window`; повтор после запуска приложения | Сначала понять политику, затем пробовать адресный `DockBarManager`; без доказательства не обещать сохранение OEM-панели |
| Системные inset не отражают OEM dock | Сравнить координаты окон и кликабельные области | Подогнать рабочую область под измерения именно целевого ГУ после теста, не закладывать произвольный размер заранее |
| OEM-виджет зависит от разрешения Launcher3 | Привязать/обновить конкретный provider в новом host | Считать OEM-виджет дополнительной совместимостью; базовый host продолжает поддерживать стандартные виджеты |
| Интерфейс GInputBridge меняется или приложение не запущено | Проверка вызова и результата на версии, стоящей в ГУ | Ограниченный версионированный контракт и независимость базового HOME от автомобильных команд |

Ни один пункт, требующий автомобильных команд или изменения режима dock, статическим анализом APK не подтверждён на реальном ГУ.
