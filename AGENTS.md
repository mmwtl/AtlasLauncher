# Repository Guidelines

## Назначение и структура

AtlasLauncher — портретный Android HOME для автомобильного ГУ OneOS, пакет приложения (`applicationId`) `com.geely.atlaslauncher`, Java-пакет и `namespace` — `com.mmwtl.atlaslauncher`. Префикс `com.geely` нужен OEM-плагину SystemUI, чтобы на HOME показывалась полная климатическая панель; не меняй его без проверки на ГУ. Это обычная Activity с Android AppWidgetHost, встроенными часами и доком приложений.

- `app/` — единственный модуль. Почти весь код — `app/src/main/java/com/mmwtl/atlaslauncher/HomeActivity.java` (~2000 строк): программный UI без XML-разметки, каталог и поиск приложений, сетка виджетов (`WidgetGrid`, `WidgetPlacement`), встроенные часы и док, окна настроек, выбор фона и сохранение состояния.
- `StockHomeRedirectService.java` рядом с `HomeActivity` — необязательная служба специальных возможностей: возвращает на Atlas, когда панель климата открывает штатный Launcher3. Конфигурация — `res/xml/stock_home_redirect.xml`, включение — флаг `stock_home_redirect` в `SharedPreferences("home")`.
- `app/src/main/res/` — встроенные фоны WebP 1086×1448 в `drawable-nodpi/`, адаптивная иконка (`mipmap-anydpi/`, монохромный вариант в `mipmap-anydpi-v33/`), векторные значки, цвета и строки. Следи за размером APK при добавлении изображений.
- `app/src/main/AndroidManifest.xml` — HOME/LAUNCHER intent-фильтры, `singleTask`, портретная ориентация и `<queries>` для Launcher3 и LAUNCHER-активностей (видимость пакетов на API 30).
- `app/build.gradle.kts` — SDK, Java, версия, имя APK и подключение подписи; корневые Gradle-файлы — конфигурация сборки.
- `docs/` — план прототипа (статус в нём мог отстать от кода) и протокол проверки/отката на ГУ; `qa/` — отчёты проверок по темам (`qa/<тема>/report.md`) и UI-дампы.
- `reference-apks/` — OEM APK и GInputBridge для анализа, описаны в `reference-apks/README.md`; `artifacts/` — ранее собранные APK 0.2.0–0.4.0, не соответствующие текущему коду. APK в обеих папках игнорируются Git.

## Сборка и запуск

Нужны JDK 17 и Android SDK API 35. Используй Gradle Wrapper (8.13, AGP 8.10.1). Текущие `minSdk=26`, `targetSdk=30`; не меняй их ради устранения предупреждений без отдельной задачи.

Из корня репозитория:

```sh
ANDROID_USER_HOME="$PWD/.android-user" ./gradlew :app:assembleDebug
ANDROID_USER_HOME="$PWD/.android-user" ./gradlew :app:lintDebug
ANDROID_USER_HOME="$PWD/.android-user" ./gradlew :app:testDebugUnitTest
```

Команды соответственно собирают debug APK, запускают Android Lint и задачу JVM-тестов. `lintDebug` сейчас завершается `BUILD FAILED` из-за единственной ошибки `ExpiredTargetSdkVersion` (следствие `targetSdk=30`); это ожидаемо. Не подавляй её, но проверяй отчёт `app/build/reports/lint-results-debug.*` на новые ошибки и предупреждения от своих изменений.

Версия задаётся `appVersionName` и `appVersionCode` в `app/build.gradle.kts`; вне ветки `main` к имени версии добавляется имя ветки. Повышай версию только по запросу, отдельным коммитом вида `Bump version to 0.5.0 (15)`. APK называется `<версия>[<versionCode>]AtlasLauncher-<тип>.apk`, например `app/build/outputs/apk/debug/0.5.0[15]AtlasLauncher-debug.apk`.

Release-сборка: `./gradlew :app:assembleRelease -x :app:lintVitalRelease` (с тем же `ANDROID_USER_HOME`); пропуск `lintVitalRelease` нужен из-за той же ошибки `targetSdk`. Подпись подключается локальным игнорируемым `secure.signing.gradle` по образцу `app/secure.signing.gradle.example` и использует общий ключ с AtlasMediaWidget; без него получается `-unsigned` APK. Debug и release подписаны разными ключами и не обновляют друг друга.

Для выбранного тестового устройства (`SERIAL` замени реальным серийным номером; путь в кавычках из-за скобок):

```sh
adb -s SERIAL install -r "app/build/outputs/apk/debug/0.5.0[15]AtlasLauncher-debug.apk"
adb -s SERIAL shell am start -n com.geely.atlaslauncher/com.mmwtl.atlaslauncher.HomeActivity
```

## Стиль кода и состояние

Следуй существующему Java-коду: отступ 4 пробела, `UpperCamelCase` для классов, `lowerCamelCase` для методов/полей, `UPPER_SNAKE_CASE` для констант; ресурсы — `lower_snake_case`. Отдельный форматтер не настроен. Предпочитай Android SDK; не вводи Compose или библиотеки ради локальной правки.

Сохраняй совместимость `SharedPreferences("home")`, JSON размещений (`widgets`) и флагов миграций (`widget_padding_migrated`, `dock_widget_migrated`). Не переименовывай строковые значения ключей, даже исторически неточные (константа `DOCK_LABELS` хранится как `drawer_labels`). Не меняй `HOST_ID`, `CLOCK_WIDGET_ID`/`DOCK_WIDGET_ID` и `WIDGET_CELL_DP` без миграции. Нижняя граница сетки `CLIMATE_PANEL_PX` задана в физических пикселях под OEM-климатическую панель, не в dp. Повторная настройка существующего AppWidget должна сохранять его ID, положение и размер при подтверждении и отмене; не смешивай её с добавлением/удалением. Учитывай восстановление Activity и различие dp/px.

## Проверка изменений

Каталогов `app/src/test` и `app/src/androidTest`, тестовых зависимостей и порога покрытия пока нет. Успех `testDebugUnitTest` без тестов не доказывает работоспособность. При добавлении JVM-тестов используй `app/src/test/java/.../*Test.java` и явно настрой тестовую зависимость.

Для UI/виджетов проверь затронутые сценарии: каталог/поиск/запуск, добавление и отмену, повторную настройку, перемещение/размер без перекрытий, часы/док и сохранение после force-stop/relaunch. Запиши устройство, версию APK, шаги, результат и ограничения в `qa/<тема>/report.md`; для визуальных изменений приложи снимки. `qa/**/*.png` и `qa/**/*.txt` игнорируются Git: снимки, на которые ссылается отчёт или README, добавляй через `git add -f`, остальные дампы не коммить. Перед сдачей выполни `git diff --check`.

## OneOS и безопасность

ГУ работает на Android 11 (API 30). API новее 30 (например, `previewLayout` виджетов из Android 12) на нём недоступны; не полагайся на них без проверки версии.

Эмулятор не подтверждает работу климата и OEM SystemUI на ГУ. Протокол выполнен на ГУ ATLAS ОД; новые изменения, затрагивающие OneOS, считай непроверенными на ГУ, пока пользователь не подтвердит. Следуй [протоколу проверки и отката](docs/head-unit-test-and-rollback.md): сначала запуск ярлыком, перед сменой HOME — фиксация исходного компонента и пути возврата. Не отключай штатный Launcher3, SystemUI или OEM-плагины. Не очищай данные при несовпадении подписей; обновления требуют того же ключа. Не коммить ключи, пароли, локальные SDK-пути и OEM APK.

## Коммиты и pull request

После каждой завершённой доработки обязательно создавай коммит с относящимися к ней изменениями, без отдельного напоминания пользователя. Перед коммитом выполни необходимые проверки; не включай чужие или несвязанные изменения.

Перед правками проверь ветку и `git status`; сохраняй чужие незакоммиченные изменения. Работа ведётся прямо в `main`. Используй короткий английский заголовок в повелительном наклонении без префиксов (например, `Keep widget grid above the climate panel`); Conventional Commits не используется.

В PR опиши проблему, итоговое поведение, проверки и ограничения; приложи снимки для UI и ссылку на задачу, если она есть. Обновляй README при изменении пользовательского поведения. Коммить и отправляй только запрошенные изменения.

## Оформление GitHub Releases

- Заголовок релиза: название проекта и версия.
- Описание — короткий список изменений для пользователя: что добавилось, что исправлено и как изменилось поведение приложения. Пиши простым языком, без внутренних деталей реализации.
- Не включай в описание технические данные: versionCode, имя пакета, SDK, подпись и сертификаты, хеши, команды сборки, результаты тестов и lint, коммиты, ветки и служебные сведения о публикации.
- Проверки сборки, подписи и артефактов выполняй как обычно; их результаты сохраняй в QA-отчётах, а не в описании релиза.
- Если изменение требует действий пользователя, укажи их кратко рядом с соответствующим пунктом.

## Стиль работы

Не соглашайся с пользователем автоматически и не хвали идеи из вежливости. Отделяй факты от предположений, прямо называй риски, противоречия, ограничения и скрытые издержки. Если идея слабая или основана на неверной предпосылке, объясни это и предложи лучший вариант. Не смягчай техническую критику, но избегай грубости и пустого негатива. При неопределённости указывай степень уверенности.

Не усложняй решение без необходимости. Вноси только те изменения, которые явно запрошены или действительно нужны для выполнения задачи.

Стремись к минимальной и понятной реализации, но не упрощай её ценой корректности, безопасности, производительности или архитектуры проекта.

- Не рефактори несвязанный код и не добавляй функциональность «на будущее».
- Не создавай лишние абстракции, обёртки, helper'ы, конфигурацию или дополнительные слои без реальной необходимости.
- Предпочитай существующий код, возможности платформы, стандартную библиотеку и уже используемые зависимости.
- Не добавляй проверки, fallback'и и обработку чисто гипотетических сценариев. При этом сохраняй необходимую валидацию, безопасность и обработку ошибок.
- Если несколько решений одинаково корректны, выбирай самое простое и требующее меньше нового кода.
- Если более сложное решение объективно оправдано требованиями, архитектурой, безопасностью, производительностью или поддерживаемостью — используй его.

Перед реализацией спроси себя: «Какое самое простое изменение полностью решает задачу без потери качества?»

Если создан план, обновляй его статус сразу после завершения каждого шага и перед переходом к следующему; не откладывай обновление всех пунктов до конца задачи.
